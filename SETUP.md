# Set up Hulog v1

Hulog records money. It does not hold, transfer, or pay out money. v1 includes
the installable PWA; v1.1 push notifications are not included.

## Local development

1. Install a current Node.js LTS release, npm, and Docker Desktop. Start Docker's
   Linux engine. From this repository run `npm ci` and `npx supabase start`.
   `supabase/config.toml` was generated by `npx supabase init`.
2. Run `npx supabase status` to find the local API URL and anon/publishable key.
   Copy `.env.example` to `.env`; set `VITE_SUPABASE_URL` and
   `VITE_SUPABASE_ANON_KEY`. Never put a service-role key in a `VITE_` variable.
3. Configure Google as described below. Local config has a disabled
   `[auth.external.google]` section: enable it, supply the client ID and secret
   through environment variables, and restart local Supabase. Set
   `auth.site_url` to `http://localhost:5173` and `auth.additional_redirect_urls`
   to include `http://localhost:5173/**` so invite paths survive sign-in.
   Email/password and other providers are not exposed by the application.
4. Run `npm run dev`. Open `http://localhost:5173`.
5. Checks: `npm run build`, `npm run lint`, `npm test`,
   `npx supabase test db`. SQL tests create disposable users; the date override
   is transaction-scoped and rolled back. The concurrent-claim test commits
   dedicated fixtures for two database connections and cleans them up.
6. When finished, run `npx supabase stop`. This stops this project's containers;
   it preserves local data. Docker Desktop itself may remain running.

`npx supabase db reset` reapplies migrations and **erases local database data**;
use it only on a disposable local instance. The project has no seed data.
Run `npx supabase start` again before database tests.

## Supabase project and Google OAuth (owner performs these)

1. Create a free Supabase project. Keep its database password private.
2. In Google Cloud Console, configure an OAuth consent screen and Web application
   OAuth client. Add test users while the consent screen is in testing mode.
   Google client credentials are server secrets, not browser environment variables.
3. In Supabase Authentication → Providers → Google, enable Google and enter the
   client ID and secret. Use the callback URL displayed there as a Google
   authorized redirect URI (cloud: `https://<project-ref>.supabase.co/auth/v1/callback`;
   local: `http://127.0.0.1:54321/auth/v1/callback`). Disable unused auth providers
   and email sign-up for this Google-only app.
4. In Authentication → URL Configuration, set Site URL to your deployed origin.
   Allow `https://<your-host>/**` plus `http://localhost:5173/**` during development.
   Hulog redirects to the original invite path following Google sign-in.
5. Log in with `npx supabase login`, link with
   `npx supabase link --project-ref <project-ref>`, inspect the pending migration,
   then apply it with `npx supabase db push`. These are manual cloud writes.
   Alternatively run the migration SQL in the project's SQL Editor, in order.
6. Set the frontend environment variables to the cloud project URL and anon or
   publishable key, then rebuild. RLS and RPC permissions govern browser access.

See Supabase's [Google provider guide](https://supabase.com/docs/guides/auth/social-login/auth-google)
and [redirect URL guide](https://supabase.com/docs/guides/auth/redirect-urls).

## Vercel (owner deploys)

Create your GitHub repository and push when ready; this build creates no remote.
Import it into Vercel with Vite preset, build command `npm run build`, output
directory `dist`. Set both `VITE_` variables before building. `vercel.json`
rewrites nested paths such as `/join/<token>` to the SPA entry point.
Add the deployed URL to Supabase's allowed redirects before inviting a partner.
For Netlify, `public/_redirects` supplies the equivalent SPA fallback.
Use HTTPS in production for service workers and clipboard support.

## Manual smoke check

Use two different Google accounts / browser profiles at a 360px viewport:

1. A signs in, creates a group, and sets "Pot held at".
2. A creates an invite. B scans its QR or opens the link, signs in, and requests
   membership. A sees B's name/email and accepts. Check the waiting screen updates.
3. A proposes a cycle starting today or tomorrow, receiver B; B accepts.
4. A records a payment (immediately confirmed). B records one (pending).
   A confirms it. Check the pot and both progress bars.
5. Open cycle details; edit B's confirmed payment. Check pending status, history
   and B's unread Changes badge. Reconfirm. Soft-delete a mistaken entry.
6. Export CSV from Group. Allow multiple downloads if the browser asks; verify
   all three files, including centavo amounts. Sign out and sign in again.
7. Once a cycle closes, check Got it for B or automatic Received for A; record,
   confirm, edit and delete a repayment where there is a debt. Database tests
   cover the deadlines without changing the production clock.
8. Try a used/revoked invite and a third account; verify errors and no data access.
   Install the PWA, reload a nested route, and verify it loads. Offline writes
   require reconnection and show an error rather than queueing money records.

## v1.1 / iOS

Push is deferred cleanly: no push tables, cron jobs, Edge Function, subscriptions,
notification controls, VAPID keys, or notification permissions are installed.
When v1.1 is implemented, generate a VAPID keypair (for example with
`npx web-push generate-vapid-keys`), put the private key and contact subject in
Edge Function secrets, and expose only the public key to the frontend. That
future implementation must include SPEC §6's dedupe and Manila scheduling.
Do not install a notification cron for this v1 build.

On iOS Safari, use Share → Add to Home Screen to install Hulog. Web Push on iOS
requires a compatible iOS version and a Home Screen installation when v1.1 exists.
